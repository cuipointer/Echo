# 2024 年 EMC Desense 类问题重点案例梳理

**目标**:从 2024 年 140 条 EMC 案例中,识别 Desense 类问题子分类,每类抽 3 个重点案例做三要素分析,形成可反哺 SOP 的结构化材料。

**数据来源**:`22~24年EMC案例总结` 飞书表格 `0L66Vr`(24年EMC问题分类整理)

## 概览:Desense 问题在 EMC 案例中的分布

### 数据源分类概览

| EMC TOP 等级 | 测试项 | 与 Desense 关系 | 案例数(估) |
|:---:|---|---|:---:|
| TOP1 | RSE | 非 Desense(辐射杂散发射) | ~40 |
| TOP2 | CE(传导发射) | 非 Desense | ~10 |
| **TOP3** | **Normal Desense** | ✅ **Desense 基准** | **~20** |
| (散列) | 场景 Desense(Display/Camera/LTE) | ✅ **Desense 场景** | **~25** |
| TOP5 | 相机抗干扰 | 反向(相机被干扰而非接收机),方法论共享 | ~15 |
| **TOP6** | **DDR Desense** | ✅ **Desense(DDR 为干扰源)** | **~15** |
| TOP7 | RE(辐射发射) | 非 Desense | ~10 |

### Desense 三子类定义

- **子类 A:Normal Desense**(基准场景灵敏度恶化)—— 未激活特定场景,系统整体噪声底线
- **子类 B:场景 Desense**(Display/Camera/LTE/CPU 等场景触发的灵敏度恶化)
- **子类 C:DDR Desense**(DDR 作为共性干扰源导致的多频段灵敏度恶化)

每子类下面选 3 个覆盖不同根因的重点案例。

## Echo 分析框架(每个案例都按此流程回溯)

所有案例按 Echo 的 6 步标准诊断流程(来自 `.claude/commands/diagnose.md` v2.0)重走一遍,便于对照 Echo 是否能覆盖真实问题、哪些地方需要补强。

| Step | 名称 | 要点 |
|:---:|---|---|
| 1 | **参数解析** | 受扰体(W24 / W5 / LLB / LHB / GL1 / GL5) + 场景(normal / lcd / ddr / rc / video / vib / fc) + 现象描述 |
| 2 | **Normal 优先** | Normal 基线 ≤ 1 dB 才能进入场景诊断;未达标则先排查 Normal |
| 3 | **宽窄带判别**(架构级筛选) | 单频 ≥ 10 dB → 窄带谐波;多信道平坦度差 → 宽带平台泄露;随配置变化 → MIPI |
| 4 | **决策树 + 矩阵查询** | 读 `knowledge/decision-tree.md` + `matrix.yaml`,按"源 × 体"定位 SOP 编号,输出候选假设按优先级排序 |
| 5 | **三要素结论** | 干扰源 / 受扰体 / 耦合路径 + 改善措施 |
| 6 | **后续动作路由** | 零成本软件验证 → 硬件整改 → 设计级改版(成本递增) |

四条工作原则贯穿全流程:**Normal 优先、宽窄带判别、软件优先、设计查阅**。

**本次案例回溯的目的**:
1. 验证 Echo 框架能否覆盖 2024 年实际 Desense 问题
2. 识别 matrix.yaml / decision-tree / SOP 的漏洞(如 A.2 的 `SHIELD_LEAK → W24` 缺失 / B.2 的 NFC 源缺失)
3. 从真实案例的耗时(A.1 快速 21 天 vs C.2 耗时 42 天)反推 SOP 需要增强的环节

## 子类 A:Normal Desense 重点案例(3 个)

### A.1 O2 WiFi 5G 5765 Normal Desense Fail 20 dB — 时钟 Spur

> **独立案例已拆出**:详见 [O2-W5-OSC-spur.md](O2-W5-OSC-spur.md)(2026-05-06 Sprint 2 拆分)

**基本信息**:

- **机型**:O2
- **阶段**:P1
- **现象**:5G WiFi 5765 MHz Normal 最差 Fail **20 dB**
- **持续天数**:21 天

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `W5` / 场景 `normal` / "5765 单频点 Fail 20 dB" | 参数完整 |
| 2. Normal 优先 | 本身即 Normal 场景,无需检查基线(直接进入架构级筛选) | 基线 = 测试自身 |
| 3. **宽窄带判别** | **单频点 20 dB** → **强窄带特征** | ✓ 保留:时钟谐波类源;✗ 排除:宽带 EMI / 电源 SSN |
| 4. 决策树 + 矩阵 | `W5` 列 + 窄带 → 候选源 `OSC / MIPI`;Normal 场景无显示/摄像激活 → **H1:OSC 倍频**(最高);对应 `W5-01` | 主假设 H1:OSC 倍频命中 |
| 5. 三要素结论 | 见下方三要素分析 | — |
| 6. 后续动作 | 零成本验证:数字滤波器 NV 调参(无需改板) → 成功 | 软件优先原则命中 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | 系统时钟(XO/OSC)倍频产生的 spur |
| 受扰体 | WiFi 5G 5765 MHz(单频点,窄带干扰特征) |
| 耦合路径 | 传导 + 辐射混合,噪声沿电源或地平面进入接收前端 |

**根因**:5765 有时钟倍频的 spur。

**解决方案**:导入**数字滤波器措施**(软件层面 NV 配置,非硬件改板)。

**架构启示**:

- 单频点 20 dB 恶化是**窄带谐波命中**典型特征,匹配 Echo 方法论的"宽窄带判别"原则 → 进入 Step 3 应立即锁定"时钟谐波命中"假设
- 对应 matrix.yaml 中 `OSC → W5` 映射(`W5-01`),该 SOP 应补充"数字滤波器 NV 调参"作为软件首选措施

- **阶段**:P1
- **现象**:2.4G WiFi chain1 Normal 信道间平坦度最差 **6.2 dB**

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `W24` / 场景 `normal` / "chain1 信道平坦度 6.2 dB" | 参数完整 |
| 2. Normal 优先 | 自身即 Normal 基准 | 基线 = 测试自身 |
| 3. **宽窄带判别** | **信道间平坦度差** → **全频段宽带特征**(区别于 A.1 单频点) | ✓ 保留:平台泄露 / 电源 SSN / 屏蔽不良;✗ 排除:窄带谐波 |
| 4. 决策树 + 矩阵 | `W24` + 宽带 → 候选源 `SHIELD_LEAK / PMIC / DDR`;chain1 靠近 CPU 位置 → **H1:CPU 屏蔽罩泄露**;矩阵中 `SHIELD_LEAK → NORMAL = NORMAL-07`(应补 `SHIELD_LEAK → W24` 映射) | H1:CPU 屏蔽泄露 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | 软件不可解 → 硬件整改(屏蔽罩改板) | 直达硬件层 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | CPU 屏蔽罩内部噪声(DDR/主芯片宽带噪声) |
| 受扰体 | WiFi 2.4G(全频段信道间平坦度差,**宽带干扰**特征) |
| 耦合路径 | **辐射**——屏蔽罩密封不良,内部噪声向外泄露到天线区域 |

**根因**:CPU 屏蔽罩内部噪声泄露。

**解决方案**:P2 回归验证整改措施(屏蔽罩加固)。

**架构启示**:

- 信道间平坦度差是 Normal Desense 的**宽带干扰**判据,与 A.1(窄带)形成对照
- 对应 matrix.yaml 新建映射:`CPU_SHIELD_LEAK → W24`(目前矩阵中暂无独立 CPU_SHIELD_LEAK 源,应合并到 `SHIELD_LEAK`)
- **Echo 方法论补充**:Normal 优先原则下,应增加"信道平坦度 ≥ N dB"作为宽带 Normal Desense 的自动判据

### A.3 O3 LTE B28 Normal 3~5 dB — 无线充弹片下方电源泄露

> **独立案例已拆出**:详见 [O3-LLB-charger-wireless.md](O3-LLB-charger-wireless.md)(2026-05-06 Sprint 2 拆分)

**基本信息**:

- **机型**:O3
- **阶段**:P1
- **现象**:LTE B28 主集/分集 Normal 值偏低 **3-5 dB**
- **持续天数**:20 天

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `LLB` / 场景 `normal` / "B28 主分集 3-5 dB" | 参数完整 |
| 2. Normal 优先 | 自身即 Normal 基准 | 基线 = 测试自身 |
| 3. **宽窄带判别** | **主分集同步偏低 3-5 dB** → **低频宽带特征**(非单频谐波) | ✓ 保留:电源 SSN / 传导类;✗ 排除:窄带时钟谐波 |
| 4. 决策树 + 矩阵 | `LLB` + 低频宽带 → 候选源 `PMIC`;查矩阵 `PMIC → LLB = LLB-04`(P0 高优先级)→ **H1:PMIC 传导**;结构补充:无线充弹片下方次表层大电源 → H2:无线充相关 | H1+H2:电源系列 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | 软件无解 → 硬件并联低频滤波电容(2 处) | 硬件层 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | 无线充弹片下方次表层的大电源(电源平面纹波) |
| 受扰体 | LTE B28 低频段(700-960 MHz) |
| 耦合路径 | **传导** —— 电源平面 → PCB 层间耦合 → 射频前端 |

**根因**:无线充弹片下方次表层为大电源,电源噪声通过 PCB 层间传导。

**解决方案**:
1. 泄露噪声处电源并联**低频滤波电容**
2. 无线充弹片处并联低频滤波电容

**架构启示**:

- "无线充 + 大电源 + B28 低频"是典型的**电源 + 物理布局**耦合,光查电源配置不够,必须看无线充结构布局
- 对应 matrix.yaml 中 `PMIC → LLB` 映射(`LLB-04`已存在),该 SOP 应补充"无线充相关场景"专项检查项
- 这类问题证明 **"设计查阅"原则** 不能光查电源原理图,要查**带 PCB 层叠 + 结构件**的综合设计

## 子类 B:场景 Desense 重点案例(3 个)

### B.1 O11 B40 DIV FrontCam 场景 16 dB — CPU 768M 三次倍频

> **独立案例已拆出**:详见 [O11-LHB-CPU-clock-B40.md](O11-LHB-CPU-clock-B40.md)(2026-05-06 Sprint 2 拆分)

**基本信息**:

- **机型**:O11
- **阶段**:P1
- **现象**:B40 DIV FrontCam 场景 Desense 最大值 **16 dB**
- **持续天数**:17 天

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `LHB`(B40 2300-2400 MHz) / 场景 `rc`(前摄)/ "DIV 16 dB" | 参数完整 |
| 2. Normal 优先 | **强制检查**(假设 ≤1 dB 达标,否则先排查 Normal) | 假设基线达标 |
| 3. **宽窄带判别** | **单频段 16 dB** → **窄带谐波强命中** | ✓ 保留:时钟类谐波;✗ 排除:电源宽带噪声 |
| 4. 决策树 + 矩阵 | 谐波计算:CPU 768 MHz × 3 = **2304 MHz** 正中 B40 低端;查矩阵 `OSC → LHB = LHB-01` 或新增 `CPU_CLOCK → LHB`;前摄场景激活 → 放大辐射路径 | H1:CPU 768M×3 命中 B40 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | 软件不可调 CPU 时钟 → 硬件:全方位导电泡棉屏蔽 | 硬件层 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | CPU 时钟 768 MHz 的**三次倍频 = 2304 MHz** |
| 受扰体 | LTE B40 DIV(2300-2400 MHz) |
| 耦合路径 | **辐射** —— CPU 屏蔽罩泄露 + 前摄激活放大辐射 |

**根因**:CPU 768M 的三次倍频打中 B40。

**解决方案**:中框加**全方位导电泡棉**(包围性屏蔽增强)。

**架构启示**:

- 16 dB 单场景恶化是极严重水平(B40 典型灵敏度 -94~-102 dBm),影响正常通话/数据
- **关键诊断点**:CPU 768M × 3 = 2304 MHz 的谐波计算,正好落在 B40 频段——这是 `/diagnose` Step 3 宽窄带判别 + 谐波命中组合能秒杀的案例
- 对应 matrix.yaml 应增加 `CPU_CLOCK(768M) → LHB` 映射,或归并到 `OSC → LHB`(`LHB-01`)
- FrontCam 场景放大辐射——说明**场景激活不仅激活了新干扰源,也可能放大既有源的辐射**

### B.2 O2 WiFi 2.4G Display Desense Fail 20 dB — NFC 谐波干扰

> **独立案例已拆出**:详见 [O2-NFC-W24.md](O2-NFC-W24.md)(2026-05-06 拆分)


**基本信息**:

- **机型**:O2
- **阶段**:P1
- **现象**:2.4G WiFi Desense Display/Touch on Fail **20 dB**(Video/Display 18 dB)
- **持续天数**:33 天

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `W24` / 场景 `lcd`(Display/Touch on)/ "Fail 20 dB" | 参数完整 |
| 2. Normal 优先 | 强制检查(假设 ≤ 1 dB 达标) | 假设基线达标 |
| 3. **宽窄带判别** | **单场景 20 dB** + Display 触发 → 两个候选模型:①Display 相关窄带(MIPI)②场景下共存干扰激活 | 需验证 |
| 4. 决策树 + 矩阵 | 首选 H1:`LCD_MIPI → W24 = W24-01`(Display 场景标配假设);但 33 天未解决说明 H1 不命中 → 回到 Step 3 重新枚举 → **H2:NFC 谐波**(NFC 13.56 MHz × 177 ≈ 2.4G);NFC 目前未在 matrix.yaml 中(缺口) | H2:NFC 共存干扰 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | 软件无效 → 硬件 PCB 改版 + 滤波网络 | 硬件层 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | NFC(Near Field Communication) |
| 受扰体 | WiFi 2.4G(2412-2484 MHz,Display/Touch 场景) |
| 耦合路径 | **传导 + 辐射** —— NFC 天线/电路噪声经射频通路耦合 |

**根因**:NFC 谐波干扰。NFC 基频 13.56 MHz,高次谐波密集落在 2.4 GHz 附近。

**解决方案**:**PCB 改版**,在射频通路增加滤波网络。

**架构启示**:

- 20 dB Desense 且**硬件改版**才解决,说明这是设计级根因
- NFC 干扰 WiFi 2.4G 是典型**同机共存**问题,应纳入 Echo **干扰源清单的"共存类"分类**(目前 matrix.yaml 没有 NFC 作为独立源)
- 建议在 matrix.yaml 中新增 source: `NFC`,category: `共存`,并新建映射 `NFC → W24`
- **Echo 方法论补充**:场景 Desense 排查时,"同频段共存源"应作为一个独立检查项

|:---:|---|---|
| 1. 参数解析 | 受扰体 `LLB`(B8 900 / B5 850 / B26 850 MHz)/ 场景 `ddr` / "3-5 dB" | 参数完整 |
| 2. Normal 优先 | 强制检查(DDR 场景本身常在 Normal 之上激活) | 假设基线达标 |
| 3. **宽窄带判别** | **多频段同步 3-5 dB** → **宽带**特征 + DDR 高频数据线噪声 | ✓ 保留:DDR 宽带辐射;✗ 排除:单点谐波 |
| 4. 决策树 + 矩阵 | `LLB` + `ddr` → `DDR → LLB = LLB-03`(矩阵命中);**耦合路径异常**:DDR 基频 200-933 MHz 不该直接落在 LB(700-960)——说明路径不是频率直达,而是**结构性辐射路径**(破洞/缝隙)| H1:DDR + 前摄破洞耦合路径 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | 1) BTB 增加滤波 2) 拆装小板支架(修正结构装配)3) 主 FPC BTB 电容滤波 | 综合措施 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | DDR(高频内存时钟及数据噪声) |
| 受扰体 | LTE LB 低频段(B8 900 MHz,B5 850 MHz,B26 850 MHz) |
| 耦合路径 | **辐射** —— DDR 噪声从**前摄破洞**处经腔体耦合到下天线;B5/B26 从电池和中框面传到下天线 |

**根因**:DDR 噪声通过前摄破洞和中框缝隙辐射泄露。

**解决方案**:
1. B8:主 FPC BTB 和屏 BTB 增加相应滤波
2. B5/B26:拆小板支架再重新组装(修正结构装配)
3. 主 FPC BTB 和屏 BTB 增加电容滤波

**架构启示**:

- DDR Desense 在 P0.1 就被发现,说明**首轮就要把 DDR 放到优先排查位**
- "前摄破洞"是一个**隐蔽的耦合路径**,matrix.yaml 中 `DDR → LLB` 目前是 placeholder(`LLB-03`),正式版应把"破洞 / 缝隙耦合路径"作为必查项
- **Echo 方法论补充**:"物理耦合路径的结构级路径"(破洞/缝隙/FPC 走向)应进入设计查阅原则的**必查清单**

### C.2 O11U MHB Desense 7-11 dB — CPU 屏蔽罩 + 主摄 FPC 噪声叠加

> **独立案例已拆出**:详见 [O11U-LHB-multisource.md](O11U-LHB-multisource.md)(2026-05-06 Sprint 2 拆分)

**基本信息**:

- **机型**:O11U
- **阶段**:P0.1
- **现象**:前后摄 DDR 场景 ANT3 MHB 多场景 Desense **7-11 dB**
- **持续天数**:42 天

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `LHB`(MHB 2300-3700 MHz,ANT3)/ 场景 `ddr + rc`(前后摄+DDR)/ "7-11 dB" | 多场景激活 |
| 2. Normal 优先 | 强制检查(假设达标) | 假设基线达标 |
| 3. **宽窄带判别** | **多场景 + 幅度 7-11 dB** + 不同场景数值差异 → 可能**多源叠加** | 需枚举多假设 |
| 4. 决策树 + 矩阵 | `LHB` + `ddr` → `DDR → LHB = LHB-03`(主);但前后摄场景放大 → H2:CPU 屏蔽泄露;H3:主摄 FPC 噪声经屏蔽-中框间隙;三假设**非互斥,同时存在** | H1+H2+H3 叠加 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | **多源叠加排查法**:逐一验证各源贡献(扩大 CPU 屏蔽铜箔 → 验证改善几 dB;再加单点接地 → 再验证);42 天耗时的主要原因是多次分离验证 | 叠加验证 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | **两个源叠加**:CPU 屏蔽罩噪声 + 主摄 FPC 噪声 |
| 受扰体 | LTE MHB ANT3(2300-3700 MHz) |
| 耦合路径 | **辐射混合** —— 主摄 FPC 噪声通过屏蔽罩与中框间隙传播到 ANT3 + CPU 屏蔽罩自身泄露 |

**根因**:
1. 部分机器 CPU 屏蔽罩泄露
2. 主摄 FPC 噪声从屏蔽罩-中框间隙传到 ANT3

**解决方案**:
1. CPU 屏蔽罩铜箔扩大,导入 2.5×8×0.3 导电泡棉
2. CPU 屏蔽罩与中框之间增加单点接地(主摄 BTB 反面位置)

**架构启示**:

- **多干扰源叠加**案例——不是单一源,而是 CPU 屏蔽 + 主摄 FPC 两个源叠加
- 这种案例 `/diagnose` Step 4 "决策树 + 矩阵查询"的输出应是**多假设清单**,而非锁死单一源
- 42 天才解决,说明**多源叠加问题**是 P0.1 高耗时代表,应该在 SOP 里加"假设互斥验证"步骤(关闭其中一个源看另一个贡献多少)
- 对应 matrix.yaml `DDR → LHB`(`LHB-03`)正式版应新增"多源叠加排查法"专节

### C.3 O11U GPS L1 DDR Desense 3 dB — PMIC 屏蔽罩顶部泄露(极敏感)

> **独立案例已拆出**:详见 [O11U-GL1-shield-aperture.md](O11U-GL1-shield-aperture.md)(2026-05-06 Sprint 2 拆分)

**基本信息**:

- **机型**:O11U
- **阶段**:P0.1
- **现象**:GPS L1 DDR Desense **~3 dB**
- **持续天数**:42 天

**分析流程(Echo 框架回溯)**:

| Step | 动作 | 输出 |
|:---:|---|---|
| 1. 参数解析 | 受扰体 `GL1`(1561-1606 MHz,敏感度 -140 dBm)/ 场景 `ddr` / "3 dB" | **GPS 敏感度极高,3 dB 即严重** |
| 2. Normal 优先 | 强制检查;GPS Normal 特别要求(通常 ≤ 3 dB) | 假设基线达标 |
| 3. **宽窄带判别** | **GPS 单频段 3 dB** + DDR 场景 → 宽带噪声通过结构路径耦合 | ✓ 保留:平台泄露/屏蔽不良 |
| 4. 决策树 + 矩阵 | `GL1` + `ddr` → 多重命中:`DDR → GL1 = GL1-03` + `PMIC → GL1 = GL1-04` + `SHIELD_LEAK → NORMAL = NORMAL-07`;定位到 **H1:BOT 面 PMIC 屏蔽罩顶部开窗**(设计级缺陷) | H1:屏蔽罩设计开窗 |
| 5. 三要素结论 | 见下方 | — |
| 6. 后续动作 | 软件无解 + 普通硬件修补无效(42 天)→ 设计级改版:PMIC 屏蔽罩**取消顶部开窗**,切换积水铜箔 | 设计级 |

**三要素分析**:

| 要素 | 内容 |
|---|---|
| 干扰源 | BOT 面 PMIC 屏蔽罩噪声泄露 |
| 受扰体 | **GNSS L1(1561-1606 MHz,敏感度 -140 ~ -150 dBm)** |
| 耦合路径 | **辐射** —— 屏蔽罩顶部开窗泄露,经 PCB 另一面耦合到 GPS 天线 |

**根因**:BOT 面 PMIC 屏蔽罩顶部开窗,噪声从开窗处辐射。

**解决方案**:**PMIC 屏蔽罩顶部开窗取消,切换为积水铜箔**(完全封闭屏蔽)。

**架构启示**:

- GPS L1 敏感度 -140 dBm,3 dB Desense 即严重影响定位——看起来数值小但实际更严重
- 对应 matrix.yaml `PMIC → GL1`(`GL1-04`)和 `DDR → GL1`(`GL1-03`)两条映射,本案例是**两个源的综合体**
- **关键启示**:屏蔽罩**"设计级开窗"**(为其他工艺便利而开)是隐蔽设计缺陷,应纳入**设计查阅必查项**
- 对照 matrix.yaml 中 `SHIELD_LEAK → NORMAL`(`NORMAL-07`,stub)正式版,应把此案例作为典型

## 综合分析与架构反哺建议

### Echo 框架覆盖度回溯

对 9 个案例按 Echo 框架重走一遍,验证每一步的命中情况:

| Step | 命中情况 | 未命中/需补强 |
|:---:|---|---|
| Step 1 参数解析 | 9/9 ✓ 受扰体 + 场景均可映射到标准术语 | — |
| Step 2 Normal 优先 | 3 个 Normal 类案例(A.1/A.2/A.3)自身即基准;6 个场景类应先验 Normal | 建议 SOP 模板强制要求"Normal 基线值"字段 |
| Step 3 **宽窄带判别** | 9/9 ✓ 均可按"单频/宽带/多场景"归类;**本步骤在本次分析中效力最强** | — |
| Step 4 决策树 + 矩阵 | 6/9 ✓ 命中现有 matrix 条目(A.1/A.3/B.1/B.3/C.1/C.3);**3 个未直接命中** | A.2 `SHIELD_LEAK → W24` 缺失;B.2 `NFC` 源缺失;C.2 多源叠加矩阵无表达方式 |
| Step 5 三要素结论 | 9/9 ✓ 均可用三要素清晰表达 | — |
| Step 6 后续动作路由 | 9/9 ✓ 均可按"软件 → 硬件 → 设计"成本递增路径规划 | 7/9 需要硬件级改动,说明"软件优先"原则在 EMC Desense 领域命中率不如常规 Desense |

**总体命中率 ≈ 85%**。主要缺口在 Step 4 矩阵层:缺 NFC 共存源、多源叠加表达、部分隐含的"源 × 体"组合(如 CPU 屏蔽 × W24)未显式定义。

**与 AS2 案例对照**:AS2 案例(知识库中 `AS2-RC-WiFi24-OIS`)是 Camera OIS Driver IC 辐射,当时 Echo 方法论中缺"OIS 驱动"分类,案例驱动了 SOP-W24-02 v2.1 更新。本次 9 个 EMC 案例也应驱动类似的**矩阵 + 方法论双重更新**。

### Desense 根因分布(基于 9 个重点案例)

| 根因大类 | 案例数 | 案例 |
|---|:---:|---|
| **系统时钟 / MIPI 高频谐波** | 3 | A.1(XO)/ B.1(CPU 768M)/ B.3(屏 MIPI) |
| **平台噪声泄露(屏蔽罩相关)** | 3 | A.2(CPU 屏蔽罩)/ C.2(多屏蔽)/ C.3(PMIC 屏蔽) |
| **电源噪声泄露** | 1 | A.3(无线充电源) |
| **共存类(NFC 等)** | 1 | B.2(NFC 干扰 WiFi) |
| **物理耦合路径(破洞/间隙)** | 1 | C.1(前摄破洞 + BTB) |

**核心洞察**:平台噪声泄露占 1/3,且大多与**屏蔽罩设计/工艺**相关。这是最应该标准化的方向。

### 反哺 Echo 架构的 6 条建议

1. **matrix.yaml 新增源**:`NFC`、`CPU_SHIELD`(独立于通用 `SHIELD_LEAK`)
2. **方法论补充:宽窄带判别**的自动判据应写入 `/diagnose` Step 3:
   - 单频点 ≥ 10 dB → 优先窄带谐波假设
   - 信道平坦度 ≥ 3 dB → 优先宽带平台泄露假设
3. **SOP 模板新增章节**:"多源叠加排查法"作为 SOP 步骤 2.6(扩展现有 W24-02 步骤 2.5)
4. **设计查阅必查项扩充**:
   - 屏蔽罩开窗设计(C.3 启示)
   - 物理耦合路径(破洞/缝隙/FPC 走向)(C.1 启示)
   - 无线充 + 大电源的层叠综合(A.3 启示)
5. **知识库新增案例**:把 C.1(O11 破洞耦合)和 B.2(NFC 干扰)正式写入 `knowledge/cases/`,前者关联 `LLB-03`,后者关联 `W24-01` 或新 SOP
6. **CHANGELOG 新增条目**:v2.1.0-rc(2026-04-28)收录 2024 EMC Desense 案例分析作为 Phase 2 内容填充的起点
